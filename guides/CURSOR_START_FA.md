# شروع عملی کار در Cursor — مرحله صفر تا انتشار

## آماده‌سازی یک‌باره
1. در GitHub یک مخزن خصوصی خالی بساز یا از مخزن فعلی ادامه بده. **فایل‌های موجود را ابتدا بررسی کن**؛ روی کد قبلی overwrite کورکورانه نکن.
2. محتوای این ZIP را خارج کن. پوشه‌های `source/`, `prompts/`, `manifests/`, `guides/` را داخل ریشه repo قرار بده. داخل `cursor-kit/`، فایل `AGENTS.md` و پوشه `.cursor/rules/` را به ریشه repo کپی کن. قوانین starter هستند؛ در S00 ممیزی و نهایی می‌شوند.
3. فایل‌های Word در `source/original-docx/` فقط برای انسان‌اند. Cloud Agent در عمل باید متن Markdown متناظر در `source/specs/` را بخواند. سه SQL در `source/technical/` صرفاً PROPOSAL هستند؛ هیچ‌کدام را مستقیماً روی Production اجرا نکن.
4. تنظیمات Cursor Cloud Environment را با مخزن/شاخه/وابستگی‌های واقعی پیکربندی کن؛ **کلیدهای API را داخل چت یا مخزن نگذار**. رابط Cloud و مدل قابل انتخاب در حساب خودت باید تأیید شود.
5. مرحله صفر را از `prompts/00_BOOTSTRAP/SHARED/` به ترتیب شناسه انجام بده. نخست `S00-001` را به Codex بده؛ مابقی پس از تثبیت rules/contract audits.

## فرستادن یک تسک به Cursor
1. از `manifests/tasks.csv` ردیف را انتخاب کن. مثلا برای دریافت داخلی `S02-...` را ببین.
2. پرامپت دقیق `prompt_path` را باز کن و **همان متن بخش «پرامپت آماده»** را در Cursor Agent ارسال کن.
3. فایل‌های `ATTACHMENTS.txt` کنار همان پرامپت را بررسی کن. اگر همه در مخزن‌اند، به مسیرشان با `@...` اشاره کن؛ اگر نیستند همین فایل‌ها را آپلود کن (Markdown/JSON/CSV برای Cloud مناسب‌تر است).
4. مدل پیشنهادی را در منوی **واقعی حساب** انتخاب کن: C=Codex، G=Grok Cloud، U=Grok Local، R=Codex برای ممیزی شواهد. Cloud محیط اجراست، نه نوع مدل.
5. یک شاخه مستقل با نام درج‌شده بساز؛ اجازه ویرایش فقط مسیر `TARGET` در پرامپت باشد. اگر تغییر دیگری لازم بود، درخواست Task جدید بده.
6. خروجی را بر اساس تغییرات Git، تست واقعی و گزارش‌ها بررسی کن؛ در صورت PASS به PR و سپس Gate مرحله منتقل کن.

## کنترل‌های اجباری قبل از هر Merge
- Diff فقط فایل اصلی تسک و تغییرات صریح مجاز را دربرگیرد؛ اگر فایل ساختار مشترک نیاز به اصلاح دارد، PR مستقل.
- تست درست/نامعتبر و سناریوی خطا اجرا شده یا با دلیل دقیق NOT_RUN ثبت شده باشد.
- نسخه JSON Schema، RBAC، سه DB و خاموشی خروجی‌ها دست‌نخورده/آزمون شده باشند.
- «انتشار واقعی» و «اتصال CMS واقعی» تا تعیین API رسمی و مجوز متوقف بمانند.
- برای هر Gate کنترل‌های پذیرش را از `prompts/GATES/GATE-XX-REVIEW.md` طبق ADR-012 اجرا کن.

## توالی مراحل و امکان کار موازی
- S00: قراردادها، ۳۰ ممیزی، قواعد و ADRها (Codex).
- S01: B01 بنیان (Codex). تا پایان Gate 01 هیچ توسعه محصولی وابسته به B01 merge نشود.
- S02: B02 داخلی و B03 خارجی در دو Cloud شاخه‌جدا، هم‌زمان فقط توکن‌های B09. هر سه وابسته به قرارداد و Mock ثابت B01.
- S03: B04؛ S04: B05؛ S05: B06؛ S06: B08 با آداپتورهای Mock؛ S07: B07؛ S08: بقیه رابط B09.
- S09: Docker Compose سه محیط، QA امنیت/قرارداد/UI/بار، CI؛ S10: گزارش پذیرش و راهنمای بهره‌برداری.
- تا گذر Gate مربوط، بسته بعدی می‌تواند روی mock کار کند ولی ادغام integration نباید ادعای کامل بودن داشته باشد.

## دستور داده شده به مدل‌ها
به هر عامل ابتدا `AGENTS.md` و `cursor-kit/.cursor/rules/` را ارجاع بده. اگر در تنظیمات واقعی پروژه `.cursor/rules/` در ریشه کپی شده است، همان مرجع اصلی خواهد بود.

## در صورت خطا
اگر Cloud Agent سند DOCX را نمی‌خواند، Markdown موجود را با @path بده. اگر مدل نام‌گذاری‌شده در حساب نیست، نزدیک‌ترین مدل واقعی را انتخاب کن و نامش را ثبت کن؛ ادعای کیفیت مدل بدون تست ممنوع. اگر API مقصد/لوگو/CMS نامشخص است، فایل mock و BLOCKED بساز، نه endpoint ساختگی.
